streaming — worked out

How bytes become events, and events become tokens on a screen

A server writes. Some time later, a browser has words on it. In between sit a transfer coding, a framing rule and a decoder, and every bug in a streaming feature lives in one of those three. This page derives Server-Sent Events, model token streaming and the TypeScript that consumes them from three things that are always true of any stream.

01

Three things always true about a stream

Streaming looks like a feature you add. It's closer to a constraint you accept: the moment a response stops arriving all at once, three things become true and stay true, whether the payload is log lines, stock ticks or a model's tokens.

  1. The pieces are not yours to choose. One write() on the server is not one read() on the client.

    The TCP stack, the proxies in between and the client's buffer all get a vote on where the boundaries fall. Code that assumes "one write, one message" works perfectly on localhost and fails the first time a payload crosses an MTU or a proxy coalesces two writes. §03's sandbox is this fact, one click at a time.

  2. Therefore a stream needs a framing rule — something that says "this unit is complete."

    Without one you cannot distinguish "nothing more yet" from "nothing more ever". SSE's rule is a blank line. The Anthropic Messages API's rule is content_block_stop. Other protocols prefix each frame with its length. The rule differs; the need for one doesn't.

  3. A stream can stop in the middle, and resuming needs somebody to have remembered a position.

    The sender can't know what arrived — that's the one thing it has no access to. Only the receiver knows what it saw, so the receiver has to say so on the way back in. That is the entire reason the Last-Event-ID header exists (§04).

Everything below is one of those three wearing a costume. A data: field held in a buffer is fact 1; a blank line is fact 2; a retry: value and a reconnect header are fact 3. So is a model's tool call arriving as JSON that isn't valid JSON yet.

02

An HTTP response that doesn't end

Before any of the streaming-specific machinery, one thing has to be true: the server must be allowed to keep writing to a response it has already started. That isn't a trick played on HTTP. It's a transfer coding, specified, and every streaming protocol on this page rests on it.

An ordinary response announces its size up front with Content-Length, which the server can only do if it already knows the size — which it doesn't, if the content is still being produced. The alternative is chunked transfer coding, and RFC 9112 states its purpose exactly:

"Chunked enables content streams of unknown size to be transferred as a sequence of length-delimited buffers, which enables the sender to retain connection persistence and the recipient to know when it has received the entire message."

Source: RFC 9112 §7.1 — HTTP/1.1 chunked transfer coding. The coding "is complete when a chunk with a chunk-size of zero is received"; until that zero-length chunk arrives, the message is simply still going.

That last clause is what a streaming endpoint exploits: it just never sends the terminating chunk. In Node you rarely touch any of this directly — writing to the response after the headers have gone out is enough — but two calls matter:

res.writeHead(200, {  'content-type': 'text/event-stream',  'cache-control': 'no-cache',  connection: 'keep-alive',})res.flushHeaders()   // send the headers NOW, don't wait for the first body writeres.write('data: first\n\n')   // ...and the response stays open

flushHeaders() is the one people miss. Without it, Node may hold the headers back until it has body bytes worth sending, so a client that waits for a response before showing a spinner waits for your first event instead of for the connection. On a slow first token — which is every model call — that is the difference between "instant" and "broken".

Note what is not here: no protocol upgrade, no handshake, no second port. This is a plain GET that hasn't finished. Everything in §03 is a convention about what to put in the body of it, which is why SSE works through anything that speaks HTTP — and why, in §09, anything that speaks HTTP a little too enthusiastically can break it.

03

SSE: the wire format

Given a response that stays open (§02), the next question is "so where does one message end?" Server-Sent Events is the standard answer, and the answer is a blank line. This section shows what that means, byte by byte.

SSE, IN ONE PARAGRAPH

Server-Sent Events is a text format for the body of an HTTP response that stays open. The server writes plain text following a few rules, and the client cuts that text into separate messages called events. There's no new protocol and no server library. Sending an event is a res.write() of a string. Data only flows one way, from server to client.

The same spec also defines EventSource, the browser's built-in SSE client. It does the cutting, the dispatching and the reconnecting for you (§04). You don't have to use it: any code that reads the response and cuts on the same rule is an SSE client too (§07). Every AI chat UI works this way.

The blank line is two newline characters

This is the whole server side of sending one event:

res.write(`data: ${JSON.stringify({ text: "The" })}\n\n`)

Look at the end of the string. \n is the newline character, a single byte (0x0A), and this string ends with two of them. Here are the exact bytes of two events, written one after the other:

data:·{"text":"The"}\n\ndata:·{…"·cat"}\n\n

· is a space · first \n ends the line data: {"text":"The"} · second \n ends a line with nothing on it, which is the "blank line" and the signal that this event is complete

So there are two levels. A single \n ends one line, and each line is one field. Two in a row, meaning an empty line, end the whole event. You need both levels because an event can have several lines. Every ⏎ below is one \n:

id: 42⏎
event: task.completed⏎
data: {"taskId":"write-intro","actor":"writer"}⏎
⏎                      ← empty line: event #1 is complete, dispatch it
data: a plain message with no id or type⏎
⏎                      ← event #2, dispatched as the generic "message"

Why a separator is needed at all

The server always puts \n\n right after a complete event. The client, though, doesn't receive "events". It receives bytes, and each read() returns whatever has arrived so far. Fact 1 says those pieces don't line up with the server's writes. Below, the colour shows which write() each byte came from:

the server wrote two events, each one complete and ending in \n\n
write() #1   data: {"text":"The"}\n\n
write() #2   data: {"text":" cat"}\n\n

the client got exactly the same bytes, cut in different places
read()  #1   data: {"text":"The"}\n\ndata: {"te
read()  #2   xt":" cat"}\n\n

So the \n\n in the middle of read #1 is not in the middle of an object. It's the end of event #1, where the server put it. What comes after it is the start of event #2, whose rest only shows up in read #2. The \n\n is how the client finds that boundary inside a chunk that holds more than one event.

A client that's even slightly busy sees this all the time. In this real run the client did something else for 300 ms, and three separate writes arrived as one read:

// server: three res.write() calls, 50 ms apart
write()  "data: {\"text\":\"The\"}\n\n"
write()  "data: {\"text\":\" cat\"}\n\n"
write()  "data: {\"text\":\" sat\"}\n\n"
// client: one reader.read()
read()   "data: {\"text\":\"The\"}\n\n
          data: {\"text\":\" cat\"}\n\n
          data: {\"text\":\" sat\"}\n\n"   ← one string, wrapped here to fit

The client keeps a buffer and cuts it on \n\n. Here is the idea in four lines:

buffer += chunk                        // whatever read() just returnedconst events = buffer.split("\n\n")    // cut on the blank linebuffer = events.pop()                  // the last piece may be unfinished: keep it for laterfor (const ev of events) show(ev)      // everything else is a complete event

Here it is traced through the two reads from the first example:

read #1 arrives
buffer = 'data: {"text":"The"}\n\ndata: {"te'
split  → [ 'data: {"text":"The"}', 'data: {"te' ]
         show() ✓ event #1        keep in buffer ─┘  (no \n\n after it yet)

read #2 arrives, and is appended to what was kept
buffer = 'data: {"te' + 'xt":" cat"}\n\n' = 'data: {"text":" cat"}\n\n'
split  → [ 'data: {"text":" cat"}', '' ]
         show() ✓ event #2      keep '' ─┘  (nothing left over)

Without the separator, data: {"te at the end of read #1 would look like a whole message, and JSON.parse would throw on it.

A real parser, like the one in the sandbox below and in every browser, goes line by line instead. It also has to handle \r\n, comments and multiple data: lines. The rule is the same: an empty line means "event complete".

This is what a 15-line node:http server sending three words ("The", " cat", " sat") actually puts on the wire. On the left is curl -N. On the right the same bytes go through cat -A, which prints every \n as $:

curl -N localhost:8765

data: {"text":"The"}

data: {"text":" cat"}

data: {"text":" sat"}

event: done
data: end

… | cat -A

data: {"text":"The"}$
$
data: {"text":" cat"}$
$
data: {"text":" sat"}$
$
event: done$
data: end$
$

That "empty line" in the terminal is what the whole format hangs on.

The fields

  • data: — the payload. Several data: lines before the blank line are joined with newlines into one event's data, which is how you send multi-line content without inventing an escape.
  • event: — the type a client can filter on with addEventListener(type, ...). Omit it and the event dispatches as the generic "message".
  • id: — the resumption checkpoint. The client remembers the last one it saw (fact 3, §04).
  • retry: — how many milliseconds the client should wait before reconnecting. The spec: if the value "consists of only ASCII digits", it is interpreted as an integer and sets "the event stream's reconnection time".
  • A line starting with : is a comment and is ignored. Servers send these as keep-alives so that idle connections aren't reaped (§09).

Two details from the spec are worth quoting, because both cause real bugs. On the colon: "Collect the characters on the line before the first U+003A COLON character (:), and let field be that string" — the field name is everything before the first colon, so a JSON payload full of colons is safe on a data: line. And on the terminator:

"Note that the last still has to end with a blank line, the end of the stream is not enough to trigger the dispatch of the last event."

Source: WHATWG HTML — Server-Sent Events, the parsing algorithm every browser's EventSource implements.

Read that twice if you are writing a server. Closing the connection does not flush the last event. A server that writes data: done\n and hangs up has sent nothing at all, and the bug looks like "the last message is missing sometimes", which is the worst kind.

04
EventSource, reconnection, and what you get for free

  
EventSource is the SSE client built into every browser. You give it a
  URL, and it makes the request, cuts the stream on blank lines and calls your handler once per
  event. Fact 3 says resuming needs the receiver to remember a position, and EventSource
  does that too. You just need to know what it does and, more importantly, what it refuses to do.

  
const es = new EventSource("/events");es.onmessage = (e) => { const ev = JSON.parse(e.data); handleEvent(ev); };es.addEventListener("task.completed", (e) => { /* only `event: task.completed` */ });

  
What you get for free: parsing, dispatch by event type, and automatic reconnection. When the
  connection drops, the browser waits the reconnection time (default, or whatever a
  retry: line last set) and opens the request again — this time announcing where it got
  to. The spec is explicit about the mechanism:

  
"The Last-Event-ID HTTP request header reports an
  EventSource object's last event ID string to the server when the user agent is to
  reestablish the connection."

  
Source: WHATWG
  HTML — Server-Sent Events.

  
So resumption is a contract with two halves, and the browser only holds up one of them. It will
  send the header; whether anything useful happens is entirely down to your server reading it and
  starting from there. A server that ignores Last-Event-ID and replays from the top
  will deliver duplicates, forever, every time a laptop lid closes.


  
What EventSource will not do

  
    
    
  • Custom headers. There is no way to set one — including
    Authorization. Your options are a cookie, a token in the query string (which lands
    in access logs), or abandoning EventSource for fetch and parsing the
    stream yourself (§07). Most production SSE code ends up in that third bucket, and this is
    usually the reason.
    • 
    
  • Anything but GET. No request body, so a streaming endpoint that needs a
    large input — a model prompt, for instance — cannot use EventSource at all.
    • 
    
  • Give up. It reconnects indefinitely. If your server is down, that is a
    client politely retrying forever; closing it is your job, via es.close().
    • 
  


  
The other design: replay everything

  
Resumption by id is not the only workable answer. A server holding a small bounded buffer can
  simply hand every new connection the whole buffer and let the client sort it out — which is what
  4th-devs does for its agent dashboard, deliberately: the client re-renders from
  scratch and de-duplicates by id, so exact resumption never has to be the server's job. It is a
  legitimate trade, and the sandbox below is the cost of getting the client half wrong.

05
The server side: where your events meet the socket

  
Writing the server is short enough to fit on a slide, which is exactly why the two
  lines that aren't about writing — the keep-alive and the cleanup — are the ones that get left
  out.

  
Here is a whole SSE handler from a real codebase, quoted unmodified:

  
res.writeHead(200, {  'content-type': 'text/event-stream',  'cache-control': 'no-cache',  connection: 'keep-alive',})res.flushHeaders()for (const past of replay()) res.write(`data: ${JSON.stringify(past)}\n\n`)const unsubscribe = subscribe(event => res.write(`data: ${JSON.stringify(event)}\n\n`))

  
Source: 4th-devs,
  05_01_agent_graph/src/server.ts (sseHandler).

  
The last line is the interesting one, and it is the seam this whole page sits on. On its left,
  subscribe belongs to an in-process event bus that has no idea who is listening — that
  is event-driven architecture, and it has
  a page of its
  own. On its right, res.write is one socket belonging to one identified browser.
  Swap the right-hand side for a Kafka producer and the left-hand side doesn't change. SSE is the
  transport; the bus is the architecture; that one line is the adapter between them.


  
The two lines that aren't in the snippet

  
// 1. Keep-alive: a comment line, ignored by the parser, that keeps the bytes flowing//    so idle proxies and load balancers don't reap the connection (§09).const ping = setInterval(() => res.write(': keep-alive\n\n'), 15_000)// 2. Cleanup: without this, every disconnect leaks a listener and a timer, and the//    bus keeps writing to a dead socket. The leak is invisible until it isn't.req.on('close', () => { clearInterval(ping); unsubscribe(); })

  
The cleanup is not optional bookkeeping. A subscriber list that only ever grows is a memory
  leak and a slow CPU leak — each dead connection still gets serialised into on every
  event — and it presents in production as "the dashboard gets slower the longer it's been up",
  which nobody debugs on the first day.






  
06
A model's tokens are an SSE stream

  
"The model streams its response" is §03 with a schema. Set stream: true
  on an Anthropic Messages API call and the response body is exactly a
  text/event-stream, with the same \n\n, the same event: and
  data: fields and the same buffering problem. The difference is that the event types
  and payloads are documented rather than made up per app.


  
Why models stream at all

  
A model produces its answer one token at a time, and a long answer takes seconds to finish.
  Without streaming, the server can only respond once the last token exists, so the user watches an
  empty box the whole time. With streaming, each piece of text goes out as its own event as soon as
  it's generated, and the words appear while the rest is still being written. The total time is the
  same. What changes is how long until the first word shows up, and in a chat UI that's the number
  users notice.


  
What is actually on the wire

  
This is one text fragment of a real response, exactly as the bytes arrive (⏎ is
  \n):

  
event: content_block_delta⏎
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":" cat"}}⏎
⏎                      ← blank line: this fragment is complete

  
The client cuts on the blank line (§03), runs JSON.parse on the
  data: line, and appends delta.text to what's on screen. That's the whole
  "typing" effect: hundreds of these small events, one after another.


  
The shape of one turn

  
One turn is a fixed sequence: message_start (the message shell, with an empty
  content array), then per content block content_block_start → repeated
  content_block_delta → content_block_stop, then message_delta
  (carrying the final stop_reason) and message_stop. A ping
  event may appear between deltas as a keep-alive with no content of its own — the same job as the
  : keep-alive comment line in §05, promoted to a typed event.

  
A tool call is a content block whose content_block_start has
  "type": "tool_use" and a partial, growing set of arguments: each
  content_block_delta for that block carries an input_json_delta with a
  partial_json string fragment, not a complete value. The fragments concatenate, and are
  only guaranteed parseable once content_block_stop closes the block.

  
Which is fact 2 again, one level up the stack. The blank line told you a line-oriented
  unit was complete; content_block_stop tells you a semantic unit is complete.
  Both exist because the alternative — guessing from the absence of more bytes — cannot distinguish
  "not yet" from "never". A client that runs JSON.parse on each fragment as it arrives
  is making exactly that guess, and it will be wrong on every tool call with more than one delta.

In a real app there are two streams, not one

  
The browser never calls the model API directly, because that would mean shipping your API key
  to every visitor. Your own server sits in the middle: it reads the model's stream and writes a
  stream of its own back to the browser.

  
1  browser     ── POST /api/chat {messages} ──────────▶ your server
2  your server ── POST /v1/messages + x-api-key ─────▶ model API
3  model API   ── SSE: content_block_delta… ─────────▶ your server
4  your server ── SSE: your own events ──────────────▶ browser

  
The simplest middle passes the bytes through unchanged. The framing survives because a
  \n\n means the same thing on both hops:

  
app.post("/api/chat", async (req, res) => {  const upstream = new AbortController();  res.on("close", () => upstream.abort());   // browser left → stop paying for tokens  const model = await fetch("https://api.anthropic.com/v1/messages", {    method: "POST",    headers: {      "x-api-key": process.env.ANTHROPIC_API_KEY,   // stays on the server      "anthropic-version": "2023-06-01",      "content-type": "application/json",    },    body: JSON.stringify({ model: "claude-opus-5", max_tokens: 1024, stream: true, messages: req.body.messages }),    signal: upstream.signal,  });  res.writeHead(200, { "content-type": "text/event-stream", "cache-control": "no-cache" });  res.flushHeaders();  for await (const chunk of model.body) res.write(chunk);   // bytes in, bytes out  res.end();});

  
In practice the middle usually does more work. It parses the model's events (§07), saves the
  finished answer to a database, counts tokens for billing, and re-emits only what the UI needs,
  e.g. data: {"text":" cat"}\n\n. That's also the point to add id: fields
  if you want resumption, because:

  
A model stream can't be resumed. Its events carry no
  id: field, so there's no Last-Event-ID to send back, and the model API
  has nothing to resume from anyway. If the connection drops halfway through an answer, that answer
  is gone. You either send the request again or keep the partial text. §04's machinery only applies
  to the stream your server writes, and only if your server buffers the generation and
  numbers its events.






  
07
Consuming a stream in TypeScript

  
§04 explained why real code often can't use EventSource: no headers,
  no request body, GET only. The replacement is fetch plus the response's
  ReadableStream — thirty lines, and one of them is a trap.

  
const res = await fetch("/api/chat", {    // your server (§06), never the model API directly  method: "POST",                       // EventSource cannot do this  headers: { authorization: `Bearer ${sessionToken}` },  // nor this (your app's login, not the model key)  body: JSON.stringify({ messages }),  signal: controller.signal,            // nor cancellation});const reader = res.body!.getReader();const decoder = new TextDecoder();const parser = createSseParser();       // cuts on the blank line, §03for (;;) {  const { value, done } = await reader.read();   // some bytes: half an event, or three  if (done) break;  for (const event of parser.push(decoder.decode(value, { stream: true }))) {    if (event.event !== "content_block_delta") continue;    const { delta } = JSON.parse(event.data);     // safe: the event is complete    if (delta.type === "text_delta") output.textContent += delta.text;  }}

  
Those last four lines are the path from bytes to words on screen. parser.push only
  returns an event once its blank line has arrived, so JSON.parse never sees half a
  line. It still might see half a tool call, which is why §06 accumulates
  partial_json instead of parsing it.

  
Two buffers are in play here and they are easy to confuse. The parser buffers a partial
  line until a newline arrives (§03). The decoder buffers partial bytes until a whole
  character arrives — and that is what { stream: true } buys. The Encoding standard
  spells out the contract:

  
"The method can be invoked zero or more times with options's stream set to true,
  and then once without options's stream (or set to false), to process a fragmented input."

  
Source: WHATWG
  Encoding — TextDecoder.decode().

  
Drop that option and the code still works — on English text. UTF-8 encodes anything outside
  ASCII as two to four bytes, and fact 1 says the chunk boundary can land anywhere, including
  between them. A decoder told the input is complete does the only thing it can with half a
  character: replaces it with U+FFFD, the replacement character. The bytes are gone;
  no later chunk can repair them.

Cancellation, which is not optional

  
A streaming request that the user navigated away from is still running, still costing money if
  a model is on the other end, and still holding a connection. AbortController is the
  only thing that stops it:

  
const controller = new AbortController();// ...pass controller.signal to fetch, then, whenever the user leaves:controller.abort();   // closes the connection; the pending read() rejects with AbortError

  
Wrap the read loop in a try/catch that treats AbortError as a normal
  exit rather than a failure, or every cancelled stream reports itself as a crash to your error
  tracker.






  
08
SSE, WebSocket, long-polling: picking one

  
SSE's limitations read like weaknesses in a feature comparison and behave like
  strengths in an operations review. The honest summary is that one of them is a real constraint and
  the rest are someone else's problem.

  

    
TransportWhat it isPick it when

    
      
SSE
        A GET that never finishes, in a text format. One direction, server to
          client. Reconnection and resumption are in the spec.
        The data flows one way: notifications, progress, logs, model tokens. It is
          ordinary HTTP, so proxies, auth, compression and observability all already work.

      
WebSocket
        A protocol upgrade to a persistent, bidirectional, framed connection —
          no longer HTTP after the handshake.
        The client genuinely sends a lot, continuously: chat typing indicators,
          multiplayer, collaborative editing. You also inherit its infrastructure: your own
          heartbeats, your own reconnect-and-resume, and middleboxes that understand none of it.

      
Long-polling
        A request that the server holds until it has something, then answers and
          the client immediately asks again.
        You need to support something ancient, or a network that mangles
          long-lived responses. Correct, simple, and it pays a full request round-trip per
          message.

    
  

  
The one genuine constraint is connection count, and it is a browser limit rather than a protocol
  one. MDN is blunt about it:

  
"When not used over HTTP/2, SSE suffers from a limitation to the maximum number of
  open connections, which can be especially painful when opening multiple tabs, as the limit is per
  browser and is set to a very low number (6)."

  
Source: MDN
  — Using server-sent events. Over HTTP/2 the ceiling is negotiated and "defaults to 100", so in
  practice this bites on HTTP/1.1 origins only — six tabs of your own app, and the seventh hangs with
  no error anywhere.

  
"But I need to send data back" is the usual argument for reaching past SSE, and
  it is usually not an argument at all: the client can make ordinary HTTP requests whenever it likes.
  A stream down and normal POSTs up is a perfectly good bidirectional system, and it is how every
  streaming model API on the market works. Reach for WebSocket when the upward traffic is
  continuous, not merely present.






  
09
What goes wrong

  
Streaming fails in a characteristic way: it works on your machine, works in
  staging, and in production the events arrive in one clump at the end, or stop after a minute. Every
  item below is a thing between your res.write and the browser deciding it knows better.

  
    
    
  • A buffering proxy. The single most common cause. nginx buffers proxied
    responses by default, which is the right call for ordinary responses and fatal for this one: your
    events queue up until the buffer fills or the response ends. Fix it with
    proxy_buffering off, or have the app send X-Accel-Buffering: no so the
    decision travels with the response rather than living in someone else's config file.
    • 
    
  • Compression without flushing. A gzip layer that waits for a full window
    before emitting does exactly what the proxy did, one layer lower. Either disable compression for
    text/event-stream or make sure it flushes per write.
    • 
    
  • Idle timeouts. Load balancers reap connections with no bytes on them —
    commonly after 60 seconds. If your stream can be quiet longer than that, the keep-alive comment
    from §05 is not a nicety, it's the thing that keeps you connected.
    • 
    
  • No cleanup on disconnect. §05's req.on('close', ...). Without
    it the subscriber list grows forever and every event is serialised for sockets nobody is reading.
    • 
    
  • Assuming one write is one message. Fact 1, and the reason §03's sandbox
    exists. It works until a payload gets big or a proxy coalesces.
    • 
    
  • Ignoring backpressure. res.write() returns false
    when the kernel buffer is full, and a producer that keeps writing anyway grows an unbounded
    queue in your process's memory. A slow client becomes your memory problem — which is the event
    loop's business, and a whole other page:
    event-loop-worked-out.
    • 
  

  
A diagnostic worth knowing, because it splits the space in half: run
  curl -N against the endpoint directly, then through your proxy. If events appear live
  in the first and arrive in a clump in the second, stop reading your application code — nothing in
  it is wrong.

The whole page in rules, and scope

  
    
    
  1. One write() is not one read(). Anything that assumes otherwise is
    correct on localhost and wrong in production.
    2. 
    
  2. Every stream needs a framing rule, because "no more bytes yet" and "no more bytes ever" look
    identical. SSE's is a blank line, which on the wire is just \n\n: one
    \n ends a field, the second ends the event. A model turn's is
    content_block_stop.
    3. 
    
  3. Closing the connection does not dispatch the last event. It needs its blank line, and the
    spec says so in as many words.
    4. 
    
  4. Streaming over HTTP is not a hack: chunked transfer coding exists to carry "content streams
    of unknown size". Remember flushHeaders().
    5. 
    
  5. Resumption is a two-sided contract. The browser sends Last-Event-ID; if your
    server ignores it, every reconnect replays duplicates. Replaying a bounded buffer instead is a
    valid design, but only with a client that de-duplicates.
    6. 
    
  6. EventSource cannot set headers, cannot POST, and never gives up. Real code
    usually ends up on fetch + ReadableStream for the first of those
    reasons.
    7. 
    
  7. Decode with { stream: true }. A multi-byte character split across chunks becomes
    U+FFFD permanently, and it only happens to text you didn't test with.
    8. 
    
  8. Cancel with AbortController, and treat AbortError as a normal exit.
    9. 
    
  9. A model's reply streams to your server, and your server streams to the browser. The
    API key never leaves the server, and a dropped model stream can't be resumed. Only the stream
    you write yourself can carry id:s.
    10. 
    
  10. Send keep-alive comments and clean up on close. One keeps proxies from reaping
    you; the other keeps you from leaking a listener per disconnect.
    11. 
    
  11. If it works with curl -N and not through the proxy, it's the proxy. Over
    HTTP/1.1 you also get six connections per browser, total.
    12. 
  

  
Left out, on purpose

  
    
    
  • The architecture on the other side of the seam. What produces the events,
    who else consumes them, what a broker guarantees about delivery and ordering — all of that is a
    different question from how bytes cross a socket, and it has its own page:
    event-driven-architecture-worked-out.
    §05's subscribe(event => res.write(event)) is the seam between the two.
    • 
    
  • WebSocket in earnest. Named and compared in §08, not built. Frames, ping/pong,
    subprotocols and scaling a stateful connection layer are a page of their own.
    • 
    
  • gRPC streaming and HTTP/2 server push. Both real, both a different
    ecosystem, and neither is what a browser talking to a JSON API reaches for.
